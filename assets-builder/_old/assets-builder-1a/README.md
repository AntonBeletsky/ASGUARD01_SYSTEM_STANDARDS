# assets-builder — два способа получить один и тот же результат

Задача одна: собрать разбросанные по папкам CSS/JS файлы front-end проекта в два документированных файла (`style.css`, `scripts.js`) с разбором зависимостей, домино-анализом и обнаружением конфликтов — чтобы шаблон можно было продавать. Решена она **дважды, но не двумя разными инструментами, а двумя разными интерфейсами к одному и тому же инструменту**:

```
assets-builder-complete/
├── README.md                  ← вы здесь
├── 1-script/                  ← способ 1: запускаете сами, из командной строки
└── 2-skill/                   ← способ 2: устанавливаете в Claude, дальше он всё делает сам
```

`2-skill/assets-builder/scripts/assets-builder.py` — это **буквально тот же файл**, что и `1-script/assets-builder.py` (тот же размер, тот же результат на одном и том же проекте — это проверено отдельным сквозным тестом, см. `2-skill/ACCEPTANCE-REPORT-skill.md`, п. 2). Скил не переизобретает логику — он оборачивает готовый скрипт и добавляет слой суждения там, где чистая автоматика сознательно останавливается и передаёт решение человеку.

## Чем способы отличаются на практике

| | 1-script (скрипт) | 2-skill (скил для Claude) |
|---|---|---|
| Кто запускает | Вы сами, из терминала | Claude — вы просто описываете задачу словами |
| Что нужно знать | Флаги CLI (`--mode`, `--on-conflict` и т.д.) | Ничего, кроме что вы хотите |
| Что происходит при конфликте (`severity: high`) | Флаг `warn`/`fail` решает заранее, до запуска | Claude останавливается и спрашивает именно про этот конфликт, объяснив последствия — не нужно заранее знать, что будет найдено |
| Где хорошо | CI/CD, регулярная пересборка, полный контроль над моментом запуска | Разовая подготовка шаблона, нет желания разбираться в флагах, нужен понятный отчёт человеческим языком |
| Что получаете | `style.css` + `scripts.js` + отчёты | То же самое + разговор о том, что найдено и почему, на естественном языке |

Если сомневаетесь — начните со способа 2 (скил): он ниже по порогу входа и в процессе покажет вам реальный CLI-вызов, который использовал, так что при желании вы в любой момент сможете перейти на прямой запуск скрипта.

## Способ 1 — `1-script/`

```bash
pip install beautifulsoup4 tinycss2 --break-system-packages
python assets-builder.py build --project ./my-template --mode extended
```

- `assets-builder.py` — сам инструмент, один файл, без зависимости от Claude.
- `example-project/` — рабочий пример: исходники + уже собранный `dist/` (можно открыть `dist/style.css` и сразу увидеть формат комментариев, не запуская ничего).
- `TZ-assets-builder-script.md` / `PLAN-assets-builder-script.md` / `ACCEPTANCE-REPORT-script.md` — техническое задание, план реализации и отчёт о валидации (все 7 критериев приёмки пройдены, найденные по пути баги задокументированы, а не спрятаны).

## Способ 2 — `2-skill/`

- `assets-builder.skill` — готовый к загрузке пакет (это zip; внутри — папка `assets-builder/` с `SKILL.md`, справочными файлами и тем же `assets-builder.py`).
- `assets-builder/` — та же папка в распакованном виде, если хочется посмотреть содержимое без разархивирования.

**Как установить** (Claude.ai — веб/десктоп/мобильный, актуально на момент подготовки, интерфейс может измениться):
1. В настройках убедитесь, что включено «Code execution and file creation» (Settings → Capabilities для личного аккаунта; для Team/Enterprise — Organization settings → Skills).
2. Customize → Skills → «+» → «Create skill».
3. Загрузите `assets-builder.skill`.
4. Включите тумблер — загруженные скилы по умолчанию выключены.

Для Claude Code вместо загрузки просто распакуйте `assets-builder/` в `~/.claude/skills/assets-builder/` (лично для себя) или `.claude/skills/assets-builder/` внутри репозитория (на проект/команду) — распаковывать `.skill` не нужно, там же лежит готовая папка.

После установки достаточно попросить словами: «собери мне все стили и скрипты из этого проекта в один файл для продажи» — остальное по `assets-builder/SKILL.md`.

## Если нужны детали устройства, а не только результат

И там, и там лежит одинаковый набор из трёх документов — ТЗ (что должно быть), план (в каком порядке и как это проверялось) и отчёт о приёмке (что реально подтверждено тестами, включая найденные и исправленные баги). Читать их не обязательно, чтобы просто воспользоваться инструментом — но если понадобится дорабатывать логику самостоятельно, это единственный источник, где решения объяснены, а не только продекларированы.

## Определения, специфичные для этого плана

Методология описана для рефакторинга существующего кода против гайда. Здесь — сборка нового инструмента против ТЗ. Термины ниже — осознанное переопределение под этот контекст, а не копирование оригинальных формулировок.

**Приоритет** (замена «severity»):

| Приоритет | Значение здесь |
|---|---|
| CRITICAL | Без этого не производится вообще никакого выходного файла — блокирует сквозной скелет инструмента |
| HIGH | Основная заявленная ценность ТЗ (то, чем инструмент отличается от «просто конкатенации» — конфликты, домино, отчёт) |
| MEDIUM | Важно на реальном масштабе, но базовый режим корректно работает и без этого |
| LOW | Донастройка, необязательные флаги |

**Тип задачи** (замена «change_type», т.к. RENAME/DELETE/REPLACE/MOVE относятся к правке существующего кода):

| Тип | Значение |
|---|---|
| IMPLEMENT | Новая логика под конкретный FR |
| INTEGRATE | Связывание уже реализованных частей друг с другом |
| TEST | Проверка против критерия приёмки |
| DOCUMENT | Оформление вывода (комментарии/отчёт), не логика |

**Формат id:** `script-{NNN:03d}`, нумерация = рекомендуемый порядок сборки.

**«Домино» в этом плане:** в оригинале — сколько мест в существующем коде затронет одно исправление. Готового кода нет, поэтому здесь домино = **сколько других задач плана напрямую зависят от завершения этой** (её блокирующая сила). Как и в оригинале — внутри одного приоритета задачи с большим домино делаются раньше.

## Phase 3 — план выполнения (чек-лист)

Порядок ниже = рекомендуемый порядок сборки (см. обоснование после чек-листа).

```
DISCOVERY (CRITICAL)
  └── [x] script-001 — обход дерева проекта; хеш/размер/mtime каждого файла (домино: 5)

CLI (CRITICAL → HIGH)
  ├── [x] script-002 — каркас: scan/build/impact/clean-cache, флаги-заглушки (домино: 1)
  └── [x] script-015 — полное связывание всех флагов §8 с реализованной логикой (домино: 1)

HTML_PARSE (CRITICAL)
  └── [x] script-003 — link/script/инлайн style,script, порядок документа, resolve путей (домино: 2)

NESTED_DEPS (HIGH)
  └── [x] script-004 — @import (с учётом media-условия), import/require → пометка "требует ручной проверки" (домино: 1)

DEP_GRAPH (CRITICAL)
  └── [x] script-005 — граф HTML→ассет / ассет→ассет; обход вперёд/назад; защита от циклов (домино: 4)

CLASSIFICATION (HIGH)
  └── [x] script-006 — shared / page-specific / orphan / vendor (домино: 4)

DOMINO-АНАЛИЗ (HIGH)
  └── [x] script-007 — транзитивное замыкание + подкоманда `impact <file>` (домино: 2)

CONFLICT (HIGH)
  ├── [x] script-008 — CSS: 3 уровня критичности (низкая/средняя/высокая по совпадению значений) (домино: 3)
  └── [x] script-009 — JS: 2 уровня критичности (дубль-тело vs разное тело) (домино: 3)

MERGE (CRITICAL) — первый реально «продаваемый» результат
  ├── [x] script-010 — style.css: топология + группировка + заголовки-комментарии + TOC (домино: 1)
  └── [x] script-011 — scripts.js: то же + обработка order-conflict (домино: 1)

REPORT (HIGH)
  └── [x] script-012 — build-report.md + build-report.json (домино: 1)

EXTENDED MODE (HIGH → MEDIUM)
  ├── [x] script-013 — карта использования: used / dynamic-suspect / unused (домино: 2)
  └── [x] script-014 — кеш + инвалидация по хешу файла (домино: 1)

ПРИЁМКА (HIGH)
  └── [x] script-016 — прогон всех 7 пунктов TZ §12 (домино: 0)
```

### Обоснование порядка

Сначала — минимальный сквозной скелет (DISCOVERY → CLI-каркас → HTML_PARSE → NESTED_DEPS → DEP_GRAPH): каждый следующий шаг сразу проверяем руками, а не в вакууме. Дальше — то, что зависит от графа (CLASSIFICATION, DOMINO), затем независимые от графа детекторы конфликтов (CONFLICT_CSS/JS зависят только от DISCOVERY, их можно делать в любом порядке между собой). MERGE — самая критичная пара, потому что это первый шаг, дающий реальный `style.css`/`scripts.js`. USAGE_MAP и CACHE — намеренно ближе к концу: это «расширенный режим», без которого базовая сборка полностью работоспособна (см. TZ §3). CLI связывается полностью и приёмка проводится в самом конце, когда есть, что связывать и что проверять.

## Phase 4 — принципы выполнения (для будущего исполнения кода)

Адаптация принципов методологии под сборку с нуля, а не правку существующих файлов:

- **«Один файл за раз»** → здесь буквально один файл (`assets-builder.py`, см. TZ §11) — принцип становится «одна категория чек-листа за раз, по порядку, не перескакивать на следующую до завершения и проверки текущей».
- **«Домино выполняется сразу»** → там, где задачи явно делят логику (например, script-013 переиспользует извлечение селекторов/идентификаторов из script-008/009) — сразу проектировать эту логику как переиспользуемую функцию, а не дублировать и рефакторить потом.
- **«Послойная обработка» и «замены от длинного к короткому»** — это техники правки существующего кода регулярками, здесь не применимы напрямую и сознательно не переносятся. Вместо них — обычный принцип: сначала happy path, затем ошибки и граничные случаи внутри каждой задачи.
- **«Валидация после каждого файла»** → валидация после каждой задачи чек-листа, не только на script-016 в конце.

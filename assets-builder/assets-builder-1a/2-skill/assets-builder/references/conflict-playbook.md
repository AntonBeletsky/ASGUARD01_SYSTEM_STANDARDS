# Плейбук по конфликтам

Правила вида «если severity=X и type=Y → действие Z». Источник истины по самим уровням критичности — реализация в `scripts/assets-builder.py` (функции `detect_css_conflicts`, `detect_js_conflicts`, `detect_js_order_conflicts`), не интуиция.

## CSS-конфликты (`conflicts.css[]`)

Критичность считается по пересечению множеств CSS-свойств между вхождениями одного селектора в разных файлах — не по тексту правила целиком.

| severity | Условие | Действие модели |
|---|---|---|
| `low` | Все вхождения идентичны, ИЛИ пересекающиеся свойства совпадают по значению | Не блокирует. Одна строка в финальной сводке, если пользователь спросит про конфликты — иначе можно не упоминать |
| `medium` | Разные, не пересекающиеся свойства (каскад скомбинирует оба без потерь) | Не блокирует. Упомянуть в сводке одной строкой: «`.btn` определён в 2 файлах, свойства разные, конфликта по факту нет» |
| `high` | Пересекающееся свойство с разным значением (реальный риск «последний в каскаде побеждает») | **Блокирует** (см. WF-3 в `SKILL.md`). Показать пользователю оба значения и то, какой файл идёт позже в итоговом порядке (значит, по умолчанию победит он) |

## JS-конфликты (`conflicts.js[]`)

Для JS нет уровня `medium` — совпадение имени в глобальной области либо безвредный дубль, либо реальный риск затирания.

| severity | Условие | Действие модели |
|---|---|---|
| `low` | Идентичное тело (по фингерпринту первых строк) — чистый дубль | Не блокирует |
| `high` | Разное тело у одинакового имени — при конкатенации последнее определение молча побеждает | **Блокирует**. Показать оба файла, спросить: оставить как есть с явным предупреждением, взять одну из версий за основу (тогда стоит предложить убрать второе определение вручную в исходниках — скрипт сам файлы не правит), или прервать (`--on-conflict fail`) |

## Order-конфликты (`conflicts.jsOrder[]`)

Возникают, только когда ДВЕ РАЗНЫЕ страницы требуют противоположного порядка для одной и той же пары файлов. Единичное отличие порядка на одной странице (например, из-за группировки vendor→shared→page-specific) в `jsOrder` не попадает — см. известное ограничение в `SKILL.md`.

**Всегда блокирует**, независимо от того, что это не помечено полем `severity` — сам факт наличия записи в `jsOrder` уже означает «автосортировка не может угодить обеим страницам». Показать пользователю обе страницы и оба требуемых порядка (`page_a`/`order_a`, `page_b`/`order_b`), объяснить, что в файл всё равно попадёт best-effort порядок с предупреждающим баннером (см. `references/comment-templates.md`), и спросить, устраивает ли это или нужно прерывать сборку (`--on-order-conflict fail`, код возврата `3`).

## `--strip-unused` (только `extended`-режим)

| Статус в `usage.*` | Что делает флаг |
|---|---|
| `unused` | Удаляется, заменяется маркером `/* removed by --strip-unused: ... */` |
| `dynamic-suspect` | **Никогда не удаляется** — это гарантия на уровне кода скрипта (см. `strip_unused_css_rules`), не только договорённость. Не обещай пользователю, что скрипт удалит `dynamic-suspect`-элементы, даже если он настаивает — предложи вместо этого показать список и решить руками |
| `used` | Не подсвечивается как кандидат вообще |

Никогда не включай `--strip-unused` по умолчанию — только если пользователь явно попросил в текущем диалоге.

## Что НЕ входит в блокирующий гейт

Классификация файлов (`shared`/`page-specific`/`orphan`/`vendor`) сама по себе не требует остановки — даже если она выглядит эвристически спорной (см. WF-5 в `SKILL.md`), это повод для поясняющей заметки в ответе, а не для вопроса пользователю перед сборкой.

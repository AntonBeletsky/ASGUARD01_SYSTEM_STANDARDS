# doc_generator.py

Генератор технической документации для фронтенд-проектов (HTML / CSS / JS).

Скрипт обходит каталог проекта, разбирает каждый HTML/CSS/JS файл с учётом
особенностей соответствующего языка, находит связи между файлами —
и структурные (`<link>`, `<script src>`, `@import`, `import`/`require`),
и смысловые (какой JS/CSS обращается к каким `#id`/`.class` в HTML) —
и собирает всё это в **один самодостаточный HTML-файл**: вся CSS и JS
самой документации встроены внутрь, при чтении не требуется интернет
и не требуется собирать/устанавливать сам документируемый проект.

Зависимости — только стандартная библиотека Python 3.9+. Ничего
устанавливать не нужно.

## Быстрый старт

```bash
python3 doc_generator.py /путь/к/проекту -o documentation.html
```

Откройте `documentation.html` в браузере.

## Опции CLI

| Флаг | По умолчанию | Описание |
|---|---|---|
| `project_dir` | — | путь к корню фронтенд-проекта (обязателен) |
| `-o, --output` | `documentation.html` | путь к результирующему файлу |
| `--title` | имя папки проекта | заголовок документации |
| `--ignore` | — | доп. glob-паттерн исключения файлов (можно повторять) |
| `--no-default-ignore` | выкл. | не исключать node_modules/.git/dist/vendor и т.п. |

## Что попадает в документацию

- **Карта каталогов** — полное дерево проекта в сайдбаре (сворачиваемые
  папки на чистом `<details>/<summary>`, без JS).
- **Обзор проекта** — количество файлов по типам, строк кода, размер,
  цветовая палитра проекта (собранная из значений цветов в CSS),
  адаптивные брейкпоинты, обнаруженные внешние библиотеки/CDN.
- **Карта зависимостей** — SVG-граф: HTML/CSS/JS файлы как узлы в трёх
  колонках, связи — сплошные линии для структурных ссылок и пунктирные
  для смысловых (DOM).
- **Карточка на каждый файл**: путь, размер, LOC, от чего зависит и где
  используется (отдельно — структурные и смысловые связи), вкладки
  «Код» (подсветка синтаксиса) и «Структура»:
  - **HTML** — title/lang/description, дерево заголовков h1–h6,
    landmark-теги, формы и их поля, изображения (с проверкой `alt`),
    все `id`/`class` на странице, комментарии.
  - **CSS** — custom properties (переменные) со swatch-превью цвета,
    медиа-брейкпоинты, `@font-face`/`@keyframes`/`@supports`, и живой
    перечень правил «селектор → комментарий автора → объявления»
    (в духе KSS/living style guide — см. «Что изучено», п. 5).
  - **JS** — импорты/экспорты (ES-модули и CommonJS), функции и классы
    с их JSDoc (описание, `@param`, `@returns`, `@example`), обращения
    к DOM (`querySelector`, `getElementById`, …), обработчики событий,
    сетевые вызовы (`fetch`/XHR/axios), TODO/FIXME.
- **«Заметки картографа»** — автоматические предупреждения: id/class,
  объявленные в HTML, но нигде не использованные; CSS-селекторы без
  соответствия в HTML; битые внутренние ссылки; изображения без `alt`.

## Архитектура (см. подробный разбор в чате)

```
scan_project()  → дерево каталогов + списки html/css/js путей
analyze_html()  → HtmlInfo   (html.parser.HTMLParser, стандартная библиотека)
analyze_css()   → CssInfo    (собственный однопроходный токенизатор)
analyze_js()    → JsInfo     (маскирование строк/комментариев + regex)
build_edges()   → список Edge (структурные и DOM-связи между файлами)
analyze_project_stats() → агрегированная статистика проекта
render_document() → сборка одного HTML через DOCUMENT_TEMPLATE (плейсхолдеры __X__)
```

Каждый файл разбирается ОДИН раз в объект `*Info`, эти объекты — общий
источник правды и для отображения кода, и для построения графа связей,
и для статистики. Сам HTML-документ — это строковый шаблон с плейсхолдерами
(`__TITLE__`, `__SIDEBAR_TREE__`, `__FILE_SECTIONS__`ит.д.), которые
заполняются один раз в `render_document()`; это сознательно не Jinja2
и не f-string/`.format()` (из-за конфликта `{}` с литеральной CSS/JS),
а простые `.replace()` — чтобы скрипт оставался однофайловым и не тянул
зависимостей.

## Известные ограничения (важно понимать)

Это **статический эвристический анализ**, а не полноценный компилятор:

- **JS разбирается регулярными выражениями**, а не настоящим AST
  (Acorn/Babel/TypeScript Compiler API в этом проекте недоступны без
  Node.js). Строковые литералы вида `'...'`/`"..."` намеренно НЕ
  маскируются (в них лежат пути импортов и селекторы), поэтому код
  внутри строк, случайно похожий на объявление функции, теоретически
  может дать ложное срабатывание. Разграничение regex-литерала `/.../`
  и оператора деления сделано по упрощённому правилу, не по полной
  грамматике JS. `querySelector(переменная)` не резолвится — только
  литеральные строки.
- **Минифицированные файлы** (эвристика: очень длинные строки)
  не разбираются детально — только считается их размер/badge, чтобы не
  захламлять документацию нечитаемым выводом.
- **CSS-парсер** — собственный токенизатор на балансировке `{}`, а не
  по формальной грамматике CSS; вложенный нативный CSS-nesting (`&`)
  и экзотические селекторы (например, запятые внутри `:is(a, b)`)
  обрабатываются приближённо.
- **DOM-связи** находятся только для явных литеральных селекторов в
  JS/CSS; элементы, создаваемые полностью динамически (например,
  через шаблонизатор на строках), в карту зависимостей не попадут.
- Скрипт **не выполняет код проекта** — это плюс для безопасности
  (можно скормить чужой непроверенный проект) и минус для точности
  (не видно того, что появляется только во время выполнения).

Если нужна 100%-точная информация о структуре JS — следующий логичный шаг
это подключить реальный парсер (см. текстовый анализ в чате, раздел
«Что стоит изучить дальше»).

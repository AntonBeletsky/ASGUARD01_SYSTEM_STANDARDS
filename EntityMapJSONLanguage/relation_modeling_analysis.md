# Связи в diagrameditor.html смоделированы неправильно — анализ и концепция исправления

## 1. Проблема, как она видна на скрине

На скрине выбрана связь `COURSE → DEPARTMENT`, `kind: association`, `multiplicity: many_to_many`. Такую связь физически невозможно развернуть ни в один SQL DDL — в реляционной БД нет синтаксиса для «многие-ко-многим» между двумя таблицами напрямую. Она либо реализуется через третью, связующую таблицу (у нас это уже правильно сделано — `COURSE_TEACHER`, `ENROLLMENT`), либо не реализуется вообще. Редактор дал создать и сохранить связь, которая не соответствует ничему, что можно выполнить как настоящую схему БД — это и есть претензия, и она справедлива.

## 2. Корень проблемы: два независимых представления одного и того же факта

Проверил прямо в файле: у `COURSE` уже есть поле
```
course__department_id : id, FK
```
и **отдельно**, никак с этим полем не связанный, существует объект связи
```
{ id:'dept_has_courses', from:'course', to:'department', kind:'aggregation', multiplicity:'many_to_one', label:'offers' }
```
Это два *разных* куска данных, описывающих *один* факт («курс ссылается на кафедру»). Ничто в коде не связывает их между собой. Отредактировать `multiplicity` у объекта связи — не значит что-либо изменить в самом FK-поле, и наоборот. Отсюда и получилось то, что на скрине: пользователь (правильно, по конструкции интерфейса) поменял `multiplicity` через дропдаун, и система это спокойно приняла — потому что дропдаун ни с чем не сверяется, кроме списка из 7 строк.

Это системная причина, а не единичный баг: **у каждой из 21 связи в модели есть ровно та же двойная бухгалтерия** — FK-поле в `fields` одной сущности и независимый объект в `relations`.

## 3. Почему это принципиально не может работать «как в SQL»

В реляционной модели связь — это не отдельная сущность, а *свойство конкретного поля*: `FOREIGN KEY (course.department_id) REFERENCES department(id)`. Отсюда следует всё остальное:

- **Кратность не выбирается, а выводится.** Если `department_id` — обычное (не `UNIQUE`) поле, то связь автоматически many-to-one: много курсов могут ссылаться на одну кафедру, потому что ничто не запрещает повторение значения. Чтобы получить one-to-one, поле пришлось бы дополнительно пометить `UNIQUE`. «many_to_many» в принципе не входит в список возможных исходов — это не значение кратности, а *признак отсутствия одной таблицы и необходимости второй*.
- **Целевое поле не любое** — SQL требует, чтобы `REFERENCES` указывал на `PRIMARY KEY` или `UNIQUE`-поле, иначе ссылочная целостность не проверяема физически.
- **many-to-many не примитив, а паттерн из двух примитивов.** У нас он уже есть, причём сделан правильно: `COURSE_TEACHER` — это не «связь», а обычная таблица с двумя FK-полями (`course_id`, `teacher_id`). Показательно, что для *этой* пары сущностей в `relations` нет ни одной строки с `multiplicity: many_to_many` — потому что она и не нужна, всё уже выражено через связку двух `many_to_one`. Проблема ровно там, где такой связки нет, а абстрактная связь между двумя обычными таблицами всё равно позволяет выбрать `many_to_many` из дропдауна, хотя физически нечему её обеспечить.

## 4. Откуда взялась эта архитектура — не случайность, а наследство спецификации

Ранее в этом разговоре уже был вопрос: «тут описание и как в реляционных БД, и как в классах ООП — всё сразу?» — да, и это осознанное свойство `EntityMapJSONLanguage`: `kind` связи (`association`/`aggregation`/`composition`/`inheritance`/… плюс `foreign_key`) — это **намеренно двойной** словарь, покрывающий и UML-диаграммы классов, и SQL-схемы одним и тем же форматом. Спецификация прямым текстом (§9.3) закрепляет, что только связи `kind: foreign_key` разворачиваются в `ALTER TABLE … ADD CONSTRAINT`; остальные виды (`association`, `aggregation`, `composition`) — это семантика уровня ООП/UML, не обязанная быть SQL-совместимой.

Когда я строил `diagrameditor.html`, я перенёс **весь** словарь связей и кратностей из спецификации в дропдауны интерфейса без разбора — включая те токены (`association`, `composition`, `many_to_many` как прямая связь), которые в контексте формата *не предполагались* как основа для SQL-редактора. Спецификация в этом не виновата — она честно поддерживает оба режима. Виноват выбор при переносе её в конкретный инструмент: не была сделана развилка «мы делаем ООП/UML-редактор» vs «мы делаем SQL-редактор», и в интерфейс просочилось и то, и то одновременно, без внутренней сверки.

## 5. Второй, менее заметный случай той же болезни: enum-сущности

Не то, о чём вы спросили, но той же природы, и стоит зафиксировать рядом, а не молчать. Пять enum-сущностей (`LessonType`, `DayOfWeek`, `AttendanceStatus`, `GradeLetter`, `SubmissionStatus`) в модели — отдельные «сущности»-коробки. В MySQL (а `dbForge Studio for MySQL` — это конкретно MySQL) `ENUM` — не таблица, а тип конкретного столбца: `lesson_type ENUM('LECTURE','SEMINAR',…)`, объявленный прямо на колонке `Lesson.lesson_type`, без отдельной сущности вообще. Тот же корень: словарь спецификации ООП-совместим (`kind: enum` как отдельный тип сущности), SQL-реальность — нет. Не поднимаю это как отдельную задачу — просто чтобы концепция ниже не оказалась половинчатой, если однажды дойдёт и до этого.

## 6. Концепция модификации `diagrameditor.html`

### 6.1 Модель данных — было / станет

Было (два независимых объекта на один факт):
```js
// внутри entity.fields:
{ id: 'course__department_id', name: 'department_id', type: 'id', key: 'FK' }
// отдельно, в relations:
{ id: 'dept_has_courses', from: 'course', to: 'department', kind: 'aggregation', multiplicity: 'many_to_one', label: 'offers' }
```

Станет (один факт, одно место):
```js
{ id: 'dept_has_courses', fromField: 'course__department_id', toField: 'department__id', label: 'offers' }
```
`from`/`to` (сущности) и кратность нигде не хранятся — вычисляются на лету из того, чем сейчас являются `fromField`/`toField`:
- сущность-источник/цель — просто владелец поля;
- кратность — `many_to_one`, если `toField` уникально (PK/UK) и `fromField` не уникально; `one_to_one`, если оба поля уникальны. Другого не бывает — это не поле для выбора, а вычисляемая подпись.

### 6.2 Взаимодействие — новый сценарий рисования связи

Клик по сущности A → клик по сущности B по-прежнему создаёт связь, но сразу открывает инспектор с двумя обязательными дропдаунами вместо `kind`+`multiplicity`:
- **FK-поле (на A)** — список полей A; если подходящего нет, пункт «+ создать новое FK-поле» (тип автоматически берётся из целевого поля)
- **Целевое поле (на B)** — список **только** PK/UK-полей B; остальные поля B в этом дропдауне не показываются вообще, потому что физически не могут быть целью FK

Пока оба поля не выбраны — связь считается черновиком (пунктирная линия), не попадает в экспорт.

### 6.3 Многие-ко-многим — не тип связи, а действие

Вместо пункта `many_to_many` в списке кратностей — отдельная кнопка тулбара **«Add many-to-many (junction table)»**: выбираете две сущности, инструмент сам создаёт третью сущность-связку с двумя FK-полями и двумя связями по правилам §6.1 — то есть автоматизирует то, что уже вручную правильно сделано для `COURSE_TEACHER`/`ENROLLMENT`, вместо того чтобы разрешать имитацию M:N там, где для неё нет опоры.

### 6.4 Развилка, которую фиксирую, а не решаю сам

Убрать дропдаун `kind` (`association`/`aggregation`/`composition`/…) полностью — вариант А: каждая связь — просто foreign key, ничего сверх этого, максимально похоже на `dbForge Studio`. Вариант Б: оставить `kind` как необязательное текстовое уточнение семантики владения (как в исходном `university_course_map.json`, где `composition` с `cascade: delete` был осмысленным сигналом) — но чисто документационное, не влияющее ни на кратность, ни на возможность связи существовать. Судя по формулировке задачи («чисто ключами, как в SQL») — вы, похоже, за вариант А, но развилка настоящая, не решаю её тихо.

### 6.5 Миграция существующих 21 связи

Не с нуля: у 19 из 21 связи FK-поле уже существует в данных (`department_id`, `teacher_id`, `room_id` и т.д. — все уже помечены `FK` в сущностях) — их достаточно механически переразметить как `fromField`/`toField` по существующим `id` полей. Только `dept_head_is_teacher` (глава кафедры) и `course_grade_fk_enrollment` не имеют явного парного FK/PK для одного из направлений — их проверить руками отдельно при реализации.

Это анализ и концепция — в `diagrameditor.html` ничего не менял.

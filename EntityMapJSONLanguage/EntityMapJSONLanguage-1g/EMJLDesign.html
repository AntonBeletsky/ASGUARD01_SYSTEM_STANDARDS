Formal validation — spec §9.4

These 9 checks pass only after stripping 29 lines of // comments from university_course_map.json — the file does not parse with a strict JSON parser as uploaded. See Finding 1.
  • Unique id across all entities — 18/18
  • Unique id across all relations — 21/21
  • Every relation's from/to references an existing entity
  • Every from_field exists on its entity
  • Every to_field exists on its entity
  • enum-typed fields have a valid ref_id
  • array fields have items_type — N/A, no array-typed fields exist
  • enum-kind entities carry no type on their fields
  • No field has both nullable: true and not_null

Findings — cross-checking the files against each other

university_course_map.json contains 29 lines of // section-divider comments (JSONC style). Standard parsers — JSON.parse(), Python's json.load(), jq — fail on it as uploaded. The spec itself only sanctions comments via the $comment/comment keys, never raw //. After stripping those 29 lines, the file parses cleanly and passes every §9.4 rule above.

The dept_has_teachers relation (kind: "aggregation") carries this comment:

"Many teachers belong to one department. Teachers can exist without a department (visiting staff), but a department cannot be deleted while teachers reference it."

But teacher.department_id is declared "nullable": false with cascade: "restrict" — the schema does not actually allow a teacher without a department, contradicting the comment. For contrast, lesson_held_in_room gets this right: room_id really is nullable: true, cascade: "set_null", and its comment ("Nullable for online-only lessons") matches the schema exactly.

The most concrete, unambiguous finding. In JSON, dept_head_is_teacher is explicitly optional: "multiplicity": "one_to_zero_one", and department.head_teacher_id is "nullable": true ("set after teachers exist").

The diagram draws it as:

DEPARTMENT }o--|| TEACHER : "headed by"

The || token on the TEACHER side means exactly one, mandatory in Mermaid's crow's-foot notation — directly contradicting the JSON's own nullable: true. The correct token for "zero or one" (o|/|o) never appears anywhere across all 21 relations in the diagram — of the 4 nullable-FK relations in the model, this is the only one where the JSON itself expressed the optionality precisely (via one_to_zero_one), and the diagram still got it wrong.

day_of_week is the only one of 5 enum entities with zero ref_id references anywhere in the model — no field, anywhere, points to it. It looks like groundwork for a recurring-schedule feature (e.g. "every Tuesday") that was never wired up: Lesson uses a concrete scheduled_date instead.

It's also incomplete: the comment calls it "ISO weekday for recurring schedule slots," but it only lists 6 values (MON, TUE, WED, THU, FRI, SAT) — no SUN. A six-day academic week is a plausible reason, but the comment doesn't say so.
